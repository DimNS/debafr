# Dev-стенд

Локальный стенд для прогона пайплайна deploy'а без настоящего приложения и без системного nginx. Вместо приложения крутится `nginx` из публичного реестра — цель не проверить само приложение, а прогнать все шаги `debafr` целиком.

```
make dev
```

Сборка идёт в `.dev/debafr`, запуск — **из `.dev/`**, поэтому конфиг, compose-файлы и `nginx.conf` лежат рядом с бинарником и ни от чего в корне не зависят.

## Версии для install и update

Образ подставляется как `nginx:<введённая версия>`, поэтому вводить нужно **тег alpine-образа**: он в ~4 раза легче debian-варианта.

| Сценарий                       | Что вводить     | Итоговый образ        |
| ------------------------------ | --------------- | --------------------- |
| Первое развёртывание (Install) | `1.28.1-alpine` | `nginx:1.28.1-alpine` |
| Обновление (Update)            | `1.28.2-alpine` | `nginx:1.28.2-alpine` |

Любая другая alpine-версия тоже подойдёт — версия нигде не зашита.

## Что проверяет стенд

Update проходит шаги `Requirements` → `Pull image` → `Deploying` → `Healthcheck` → `Replacer` → `Switching strategy` → `Stopping current deploy`. На install шаги `Replacer` и `Switching strategy` не выполняются: новые контейнеры уже работают, а конфиг должен быть готов к первой стратегии заранее.

`Replacer` меняет blue-значения на green (и наоборот) в `debafr.json` и `nginx.conf`. `Switching strategy` после этого выполняет `nginx -t` и `nginx -s reload` командами из секции `[nginx]`.

`nginx.conf` специально содержит `/ws` на том же порту, что и `/`. Замена глобальная и должна поменять **оба** location'а разом — если после update один из них остался blue, это регресс.

Порты: blue `3001/3002`, green `3011/3012`, внешний nginx слушает `8080`.

`nginx.conf` содержит по одной активной строке `proxy_pass` на location: приложение не комментирует и не раскомментирует варианты, а заменяет адреса целиком. Начальное состояние — blue.

## Что означают коды ответа

`/` отдаёт `200` — это дефолтная страница образа `nginx`. `/api` и `/ws` дают `404`: образ-пустышка не знает таких путей, но `404` приходит **из контейнера**, значит `proxy_pass` сработал. Непрохождение прокси выглядит иначе — `502` или таймаут.

## Прямой доступ

```bash
make dev-status                     # что сейчас задеплоено
curl -i http://127.0.0.1:8080/api   # через прокси на активную стратегию
curl -i http://127.0.0.1:8080/ws    # второй location на том же порту
cat .dev/debafr.json                # цель после шага Replacer
```

`make dev-up` поднимает compose руками, минуя TUI (версия — в `APP_VERSION`).

## Уборка

```bash
make dev-down   # контейнеры приложения и тестовый nginx
make dev-clean  # плюс образы nginx и debafr.json
```

`debafr` ничего не удаляет за собой: остановленный стек остаётся в docker, и это нужно — на нём проверяется, что следующий deploy найдёт текущий.

## Файлы

| Файл                                       | Роль                                                                 |
| ------------------------------------------ | -------------------------------------------------------------------- |
| `debafr.toml`                              | конфиг приложения; читается из CWD                                   |
| `compose.blue.yaml` / `compose.green.yaml` | фейковое приложение, два стека в одном compose-проекте `debafr`      |
| `nginx.conf`                               | server-блок с одним активным `proxy_pass` на location                |
| `debafr.json`                              | файл для шага `Replacer`; `make dev` создаёт его, если его нет       |
| `nginx.sh`                                 | подмена `nginx` через `docker exec` в контейнере `debafr_test_nginx` |
